(1) YAML
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

YAMLは，シーケンス(Rubyでの配列)とマッピング(Rubyでのハッシュ，一般に
は連想配列など)とスカラー(文字列や数値等のデータ)を記述することができ
るフォーマットである．YAMLでは行単位で解釈を行い「 - スカラー 」のよう
に先頭にハイフンがあるとシーケンス，「 スカラー1: スカラー2 」のように
コロンを挟むとマッピングとなる．シーケンスやマッピングの中に，シーケン
スやマッピングをネストさせることも可能である．YAMLでは階層を半角スペー
スによるインデントで表現する．

YAML形式で記述するうえでの制限として，「*」「&」が先頭に来るような文字
列を記述したい場合や，「NULL」という文字列を記述したい場合はダブルクォー
テーションで文字列を囲む必要がある．

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
(2) TESRY記法仕様
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TESRY記法はYAML1.0に準拠する．

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
(3) TESRYデータ仕様
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TESRYデータはTESRY記法により記述されたテキストファイルである．1つの
TESRYデータには1つのYAMLドキュメントを，1つのTESRYデータには1つのテスト
シナリオを記述できる．文字コードはASCII，改行コードはLFとする．マルチバ
イト文字列は記述できない．

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
(4) TESRYデータの全体像
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

TESRYデータはテストIDとテストシナリオのハッシュから成り，それぞれのテス
トシナリオは前状態・処理・後状態の3つの要素のハッシュとなる．

・前状態: どのような状態でテストを始めるか
・処理  : システムサービスやシステムサービスを呼び出す処理単位，戻り値
          など
・後状態: 処理に記述した内容を実行後，どのような状態になるか

前状態と後状態にはオブジェクトの状態を定義する．処理にはるシステムサー
ビスの内容や実行する内容について記述する．その他の構成要素にはプロパティ
が存在する．TESRYデータに記述可能なオブジェクトやオブジェクトの属性，処
理の属性については，param.txtを参照する．プロパティに記述可能な属性，値
については，filtering.txtを参照する．

テストIDはテストプログラムの中で関数名やオブジェクトIDの先頭に付与する．
そのためアルファベットで始まり，英数字と_(アンダースコア)のみからなる文
字列でなければならない．また，テストIDには以下の制約がある．

・TTGに入力する全TESRYデータでテストIDはユニークに付ける必要がある
・"TTG_"，"ErrorHook"から始まるテストIDは予約語として指定できない

これらの概念を次の例に示す．

例) テストシナリオの全体像
======================================================================
テストID:
  前状態:
    オブジェクトID:
      type  : オブジェクトの種類
      属性1 : 値1
      属性2 : 値2

  処理:
    id      : システムサービスを発行する処理単位
    syscall : 発行するシステムサービス
    ercd    : システムサービスの戻り値

  後状態:
    オブジェクトID:
      属性1 : 値1
      属性2 : 値2
======================================================================

具体例として下記のテストシナリオで説明する．
テストIDがtest1のテストシナリオを表しており，前状態・処理・後状態を定義
している．前状態ではタスクオブジェクトのTASK1とTASK2が存在し，TASK1が実
行状態でTASK2が休止状態にである．処理では前状態で定義した状態からTASK1
がActivateTaskのシステムサービスを発行するテスト内容を記述している．そ
して，後状態ではシステムサービス発行後のオブジェクトの状態としてTASK2が
実行可能状態に遷移したことを表している．

例) テストシナリオ
======================================================================
test1:
  pre_condition:
    TASK1:
      type : TASK
      tstat: RUNNING
    TASK2:
      type : TASK
      tstat: SUSPENDED

  do:
    id     : TASK1
    syscall: ActivateTask(TASK2)
    ercd   : E_OK

  post_condition:
    TASK2:
      tstat: READY
======================================================================

(5) テストシナリオ構成要素の文法
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

本章では，前状態，処理，後状態，プロパティの文法を規定する．

―――――――――――――――――――――――――――――――――――
(5.1) 前状態 (pre_condition)
―――――――――――――――――――――――――――――――――――

前状態と前状態のオブジェクト定義部の文法として以下を規定する．

・前状態はテストシナリオ構成要素の1つである
・前状態はマッピングとする
・前状態のテストシナリオ構成要素ラベルはpre_conditionとする
・前状態は1つのテストシナリオに1つ定義する必要がある
・前状態直下の階層にはオブジェクトを定義する
・前状態にはシステムサービス発行前のシステムの状態として存在するオブジェ
  クトを定義する
・オブジェクトは任意の数だけ定義できる

例) 前状態
======================================================================
pre_condition:
  TASK1:
    type   : TASK
    tstat  : RUNNING
  RESOURCE1:
    type   : RESOURCE
    resprop: AK_STANDARD
    lockflg: AK_UNLOCK
======================================================================

―――――――――――――――――――――――――――――――――――
(5.2) 処理 (do)
―――――――――――――――――――――――――――――――――――

処理の文法として以下を規定する．

・処理はテストシナリオ構成要素の1つである
・処理はマッピングとする
・処理のテストシナリオ構成要素ラベルはdoまたはdo_N(nは整数，N > 0)とす
  る
・doと記述された場合はdo_0と同義になる．do_NのNにあたる数値をシーケンス
  番号とする
・処理は1つのテストシナリオに1つ以上定義する必要がある．ただし，同一テ
  ストシナリオ内に同じシーケンス番号を持つ処理を定義することはできない

―――――――――――――――――――――――――――――――――――
(5.3) 処理内容
―――――――――――――――――――――――――――――――――――

処理内容の文法として以下を規定する．処理内容には直前の状態から行う任意
の処理の詳細を指定する．

・システムサービス発行元の処理単位をidに指定する
・処理内容をsyssrv記述する(システムサービス以外も指定可能)
・処理内容以降の後状態でシステムサービス発行元のオブジェクトが実行状態
  になる場合は戻り値を指定する
・戻り値は型をrettypeに値をretvalに指定する
・処理内容以降の後状態でシステムサービス発行元のオブジェクトが実行状態
  にならない場合は戻り値を指定できない

例) 処理
======================================================================
do:
  id     : TASK1
  syssrv : GetResource(RESOURCE1)
  rettype: StatusType
  retval : E_OK
======================================================================

―――――――――――――――――――――――――――――――――――
(5.4) 後状態 (post_condition)
―――――――――――――――――――――――――――――――――――

後状態の文法として以下を規定する．

・後状態はテストシナリオ構成要素の1つである
・後状態はマッピングとする
・後状態のテストシナリオ構成要素ラベルはpost_conditionまたは
  post_condition_N(Nは整数，N > 0)とする
・post_conditionと記述された場合はpost_condition_0と同義になる
・post_condition_NのNにあたる数値をシーケンス番号とする
・後状態は1つのテストシナリオに1つ以上定義する必要がある

―――――――――――――――――――――――――――――――――――
(5.5) 後状態のオブジェクト定義部
―――――――――――――――――――――――――――――――――――

後状態のオブジェクト定義部の文法として以下を規定する．

・後状態のオブジェクト定義部はマッピングとする
・後状態直下の階層にはオブジェクトを定義する
・後状態のオブジェクト定義部にはシステムサービス発行後のオブジェクトを
  定義する
・後状態のオブジェクト定義部で定義可能なオブジェクトは，前状態で定義し
  たオブジェクトに限る
・後状態のオブジェクト定義部では直前の状態から変化のないオブジェクトの
  記述は省略できる
・後状態のオブジェクト定義部では直前の状態から変化のないオブジェクトの
  属性の記述は省略できる．ただし，オブジェクト情報が空のオブジェクトは
  記述できない(オブジェクトの記述自体を省略すればよい)

例) 後状態
======================================================================
post_condition:
  TASK1:
    tstat: READY
  TASK2:
    tstat: RUNNING
======================================================================

―――――――――――――――――――――――――――――――――――
(5.6) プロパティ (property)
―――――――――――――――――――――――――――――――――――

プロパティの文法として以下を規定する．

・プロパティはテストシナリオ構成要素の1つである
・プロパティのテストシナリオ構成要素ラベルはpropertyとする
・プロパティは1つのテストシナリオに必要な場合に1つ定義できる
・プロパティはマッピングとする
・プロパティではターゲット依存のテストシナリオを判別するための属性や
  テストの本質とは異なる付加的な属性を定義する

例) プロパティ
======================================================================
property:
  sc:
    - SC1
    - SC2
  need_stack_share: true
======================================================================

propertyに設定できる項目については，以下の各章で定義する．
また，propertyの設定値によるフィルタリングについては，AKTFフィルタリン
グ仕様書(filtering.txt)を参照すること．

----------------------------------------------------------------------
(5.6.1) sc
----------------------------------------------------------------------

意味  : スケーラビリティクラス
型    : 配列(複数指定可能)
有効値:
   値   | 意味
  ----------------------------------------------------------
   SC1  | スケーラビリティクラスがSC1の場合，テスト実施可能
   SC2  | スケーラビリティクラスがSC2の場合，テスト実施可能
   SC3  | スケーラビリティクラスがSC3の場合，テスト実施可能
   SC4  | スケーラビリティクラスがSC4の場合，テスト実施可能
   (空) | 全てのスケーラビリティクラスでテスト実施可能

----------------------------------------------------------------------
(5.6.2) need_enadis_interrupt_source
----------------------------------------------------------------------

意味  : システムサービスのEnableInterruptSource/
        DisableInterruptSourceが必要なテストケースか
型    : 真偽値
有効値:
   値    | 意味
  ----------------------------------------------------------------------------------------------------------------
   true  | システムサービスのEnableInterruptSource/DisableInterruptSourceをサポートしているターゲットのみ実行可能
   false | システムサービスのEnableInterruptSource/DisableInterruptSourceをサポートしていないターゲットも実行可能
   省略  | falseの場合と同じ

----------------------------------------------------------------------
(5.6.3) violation_handling_level
----------------------------------------------------------------------

意味  : テスト実行に必要な保護違反時処理機能の機能レベル
型    : 整数
有効値:
   値   | 意味
  ----------------------------------------------------------------------
   1    | 保護違反時処理機能の機能レベルが機能レベル1以上のOSで実行可能
   2    | 保護違反時処理機能の機能レベルが機能レベル2以上のOSで実行可能
   3    | 保護違反時処理機能の機能レベルが機能レベル3以上のOSで実行可能
   省略 | 1の場合と同じ

----------------------------------------------------------------------
(5.6.4) timing_protection_level
----------------------------------------------------------------------

意味  : テスト実行に必要なタイミング保護機能の機能レベル
型    : 整数
有効値:
   値   | 意味
  ----------------------------------------------------------------------
   1    | タイミング保護機能の機能レベルが機能レベル1以上のOSで実行可能
   2    | タイミング保護機能の機能レベルが機能レベル2以上のOSで実行可能
   3    | タイミング保護機能の機能レベルが機能レベル3以上のOSで実行可能
   省略 | 1の場合と同じ

----------------------------------------------------------------------
(5.6.5) memory_protection_level
----------------------------------------------------------------------

意味  : テスト実行に必要なメモリ保護機能の機能レベル
型    : 整数
有効値:
   値   | 意味
  ------------------------------------------------------------------
   1    | メモリ保護機能の機能レベルが機能レベル1以上のOSで実行可能
   2    | メモリ保護機能の機能レベルが機能レベル2以上のOSで実行可能
   3    | メモリ保護機能の機能レベルが機能レベル3以上のOSで実行可能
   省略 | 1の場合と同じ

----------------------------------------------------------------------
(5.6.6) need_stack_share
----------------------------------------------------------------------

意味  : スタック共有が必要なテストケースか
型    : 真偽値
有効値:
   値    | 意味
  ---------------------------------------------------------------
   true  | スタック共有が必要なテストケース
   false | スタック共有が必要ではないテストケース
   省略  | falseの場合と同じ

----------------------------------------------------------------------
(5.6.7) maintask_wait
----------------------------------------------------------------------

意味   :メインタスクが待ち状態に入る(実行状態のタスクを不在とする)必要
        があるテストケースか
型     :真偽値
有効値 :
   値    | 意味
  ---------------------------------------------------------------
   true  | メインタスクが待ち状態に入る必要があるテストケース
   false | メインタスクが待ち状態に入る必要がないテストケース
   省略  | falseの場合と同じ

----------------------------------------------------------------------
(5.6.8) application_mode
----------------------------------------------------------------------

意味   :configure.yamlのapp_mode_nameをStartOSの引数に指定しない場合の
        アプリケーションモードの指定(use_maintaskがfalseの場合に使用す
        る)
型     :文字列

----------------------------------------------------------------------
(5.6.9) add_osap_error_hook 【SC1-MCのみ】
----------------------------------------------------------------------

意味  : OSAP固有のエラーフックとOSAP固有のエラーフックによるエラーチェ
        ックの追加が必要なテストケースか
型    : 真偽値
有効値:
   値    | 意味
  ---------------------------------------------------------------
   true  | OSAP固有のエラーフックの追加が必要なテストケース
   false | OSAP固有のエラーフックの追加が必要ではないテストケース
   省略  | falseの場合と同じ

----------------------------------------------------------------------
(5.6.10) single_only 【シングルコアのみ】
----------------------------------------------------------------------

意味  : シングルコアでのみ実行可能なテストか
型    : 真偽値
有効値:
   値    | 意味
  ---------------------------------------------------------------
   true  | シングルコアでのみ実行可能なテストケース
   false | マルチでも実行可能なテストケース
   省略  | falseの場合と同じ

----------------------------------------------------------------------
(5.6.11) extended_return_status 【SC1，SC1-MCのみ】
----------------------------------------------------------------------

意味  : エラー種別が拡張エラーでのみ実行可能なテストか
        返り値の型がStatusTypeでないシステムサービスでのみ使用
        IncrementCounterの満了処理でエラーが発生する場合も含む
        (IncrementCounterの戻り値はE_OKだが，その後の満了処理でエラーと
         なり拡張エラーが返るケースがあるため)
型    : 真偽値
有効値:
   値    | 意味
  ---------------------------------------------------------------
   true  | 拡張エラーでのみ実行可能なテストケース
   false | 標準エラーでも実行可能なテストケース
   省略  | falseの場合と同じ

(6) オブジェクトの文法
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

本章では，前状態と後状態に記述するオブジェクト定義部の文法について規定
する．オブジェクト定義部とは，前状態と後状態に記述する，キー: オブジェ
クトID，値: オブジェクト情報で構成されるマッピングである．

例) オブジェクト
======================================================================
TASK1:
  type  : TASK
  tstat : RUNNING
  curpri: 10
COUNTER1:
  type  : COUNTER
  mincyc: 10
  maxval: 100
  curval: 50
  ctype : AK_SOFTWARE
======================================================================

―――――――――――――――――――――――――――――――――――
(6.1) オブジェクトID
―――――――――――――――――――――――――――――――――――

オブジェクトIDは半角英数字，_(アンダーバー)で構成する．ただし，1文字目
は半角英字とする．

―――――――――――――――――――――――――――――――――――
(6.2) オブジェクト情報
―――――――――――――――――――――――――――――――――――

オブジェクト情報の文法として以下を規定する．

・オブジェクト情報はマッピングとする
・オブジェクト情報直下の階層にはオブジェクト属性を定義する
・前状態に記述するオブジェクト情報にはオブジェクトのタイプ属性を指定す
  る
・後状態に記述するオブジェクト情報にはオブジェクトのタイプ属性を指定で
  きない

―――――――――――――――――――――――――――――――――――
(6.3) オブジェクト属性
―――――――――――――――――――――――――――――――――――

オブジェクト属性の文法として以下を規定する．

・オブジェクト属性はマッピングとする(キー: 属性名，値: 属性値)
・定義できるオブジェクト属性はオブジェクトのタイプごとに決定する

オブジェクトのタイプごとの属性一覧はparam.txtを参照する．

(7) 複数のタイミングで状態を確認するテストシナリオ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

処理と後状態を複数定義して，複数のタイミングで状態を確認するテストシナ
リオを表現できる．実行と確認の順序はシーケンス番号によって決定する．シ
ーケンス番号が小さい処理を実行し，処理のシーケンス番号と同じシーケンス
番号を持つ後状態を確認する．1つのシーケンス番号に対して，対応する処理と
後状態が定義されなければならない．

例) 複数のタイミングで状態を確認するテストシナリオ
======================================================================
ActivateTask_normal:
  property:
    sc: 
      - SC1
      - SC2

  pre_condition:
    TASK1:
      type: TASK
      tstat: READY
    TASK2:
      type: TASK
      tstat: RUNNING

  do_0:
    id: TASK2
    syssrv: TerminateTask()

  post_condition_0:
    TASK1:
      tstat: RUNNING
    TASK2:
      tstat: SUSPENDED
      bootcnt: 1

  do_1:
    id: TASK1
    syssrv: ActivateTask(TASK2)
    rettype: StatusType
    retval: E_OK

  post_condition_1:
    TASK2:
      tstat: READY
======================================================================

(8) テストシナリオの実行順序
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

テストシナリオはまず前状態から始まる．そしてシナリオ内に存在するシーケ
ンス番号の順番に処理，後状態と確認する．
